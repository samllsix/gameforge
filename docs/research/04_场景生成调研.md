# M4 · 场景生成调研

> **调研范围**：`src/agents/scene_generator/`、`src/agents/scene_ir.py`、`src/agents/scene_ir_to_desc.py`、`src/agents/scene_templates.py`、`src/engine/godot/scene_builder.py`、`src/engine/godot/scene_to_godot.py`（共 6 个文件 3663 行）+ `workflow.py` 中调用它的部分。
>
> **一句话结论**：这一层**本身设计不差**（四级降级 + IR 中间表示），但有两个獨立问题：**接线位置错了**（本该由 leader 按任务分派，实际从侧门并行钻进来，导致计划里的场景任务被假装完成、与代码生成互相不知情、还要一个删引用补丁善后）；**产出先天不足**（IR 只有 4 个维度、没有任何视觉字段，所以输出必然是三个纯色方块）。

---

## 1. 模块职责：设计与工程之间的那一层

把抽象的游戏设计变成 Godot 能识别的节点树：

```
GDM（游戏设计模型：有什么实体、什么玩法）
   ↓  本模块
Scene IR（中间表示：Player×1、Ground×1、Platform×3…）
   ↓
scene_description JSON（带坐标与脚本引用的对象树）
   ↓
.tscn 文件（Godot 场景）
```

具体负责四件事：

| 职责 | 载体 |
|---|---|
| 决定场景里**有哪些节点**、各多少 | `SceneIR.entities` |
| 决定节点**摆在哪** | `EntityIR.spawn_zone`（left/right/center/bottom/top） |
| 决定节点**挂什么脚本** | `EntityIR.script` → `role_script` 映射 |
| 产出 `.scene_ir.json` 供预览端点重建 | `_persist_scene_ir`（workflow.py:557） |

**它不管代码逻辑**（code_generator 的活），**也不管画面好看与否**（IR 里没有视觉字段，见 §4）。

## 2. 真实结构：四级降级

`_generate_scene_description()`（`scene_generator/__init__.py:195`）四级降级：

| 级别 | 手段 | 说明 |
|---|---|---|
| Level 1 | **模板匹配** → 确定性 IR | `scene_templates.py` 5 套硬编码模板（platformer/shooter/rpg/puzzle/runner） |
| Level 2 | **LLM 生成 Scene IR** → Pydantic 校验 | 让 LLM 直接产 IR |
| Level 3 | **品类感知 fallback IR** | 需求关键词 → 20 个品类规格蓝图 → `default_scene_ir()` |
| Level 4 | 硬编码兜底场景（无 IR） | `_fallback_scene()`，最终手段 |

`scene_ir` 是本模块的核心中间表示，落盘为 `.scene_ir.json`；预览端点据此重建场景（P0-1 改造的核心：不再硬编码抢跑）。

## 3. 接线现状：走侧门，绕过整套分发

### 3.1 设计意图：与 code_generator 平级，归 leader 调度

planner **本来就会产出 scene 类型的正式任务**（`planner/__init__.py:243`）：

```python
{"type": TaskType.SCENE.value, "id": "task_xxx", "name": "构建游戏场景", ...}
```

设计意图是：

```
planner 产出任务清单（含 scene 任务，依赖排在 code 之后）
   ↓
orchestrator 按类型分派：code → code_generator / scene → scene_generator
   ↓
scene_generator 执行 → 返回场景 → 标记 completed
```

### 3.2 实际代码：三个硬事实

| 设计意图 | 实际 |
|---|---|
| planner 排 scene 任务 | ✅ 确实排了 |
| orchestrator 分派给 scene_generator | ❌ **没有**。scene 任务命中 `_NON_CODE_TASK_TYPES`（`workflow.py:526`）→ "跳过但标记完成" |
| scene_generator 按任务执行 | ❌ 它由 `workflow._run_scene_generation()`（:589）用 `asyncio.create_task` 直接拉起，**跑在图外，与 LangGraph 主图并行** |
| 图里有 scene 节点 | ❌ 图 5 个节点中没有它，其成功/失败不进任务状态机 |

### 3.3 实测证据

stub 模式跑一次生成，任务清单：

```
task_001  type=code           status=completed  实现PlayerController
task_002  type=code           status=completed  实现GameManager
task_003  type=code           status=completed  实现CoinController
task_004  type=scene          status=completed  构建游戏场景      ← 被跳过但标记完成
task_005  type=documentation  status=completed  生成项目文档       ← 同上
```

日志对应 `task_skipped_non_code ... type=scene`。**task_004 不是被 scene_generator 完成的。**

### 3.4 侧门设计的直接后果：需要一个删引用的补丁

因为场景生成与代码生成**并行**，scene 可能引用还没写完的脚本，于是 workflow 里必须有补丁方法 `_sanitize_scene_scripts()`（`workflow.py:1329`）——把场景里引用了但代码还没生成的脚本删掉：

```
场景生成（图外并行）──┐
                      ├──→ 场景引用 PlayerController，但代码还没写完
代码生成（图内）──────┘         ↓
                        _sanitize_scene_scripts() 把引用删掉
```

**如果按设计让 scene 任务排在 code 之后串行执行，这个补丁根本不需要存在。**

## 4. 产出质量瓶颈：IR 先天没有视觉字段

### 4.1 实体蓝图只有 4 个维度

```python
class EntityIR(BaseModel):        # src/agents/scene_ir.py:43
    name: str                     # 名字
    role: str                     # player/enemy/pickup/ground/platform/decoration…
    count: int                    # 数量
    spawn_zone: str               # left/right/center/bottom/top
    script: Optional[str]
```

以 platformer 品类为例，规格蓝图产出：

```
Player    ×1  spawn_zone=left
Ground    ×1  spawn_zone=bottom
Platform  ×3  spawn_zone=center
Coin      ×3  spawn_zone=center
Goomba    ×2  spawn_zone=right
Tree      ×2  spawn_zone=left
```

**IR 里没有颜色、尺寸、贴图、动画、形状**。渲染时这些只能变成不同颜色的 ColorRect/CollisionShape——这就是"三个方块"的**根本原因**：不是没配 AI 生图，是**IR 这个数据结构里就没有"长什么样"的字段**。

### 4.2 20 个品类只有 5 套模板

```
品类规格库（genre_specs）: 20 个
场景模板（scene_templates）: 5 个（platformer/shooter/rpg/puzzle/runner）
未覆盖: snake, breakout, flappy, tower_defense, farming_sim, survivors,
        racing, match3, sokoban, minesweeper, merge_2048, pong, rhythm,
        clicker, word_guess   ← 15 个（75%）
```

Level 1 命中率极低；未覆盖品类全部掉到 Level 3 的 `default_scene_ir()`（`scene_to_godot.py:1588`），即拿品类规格表做确定性拼接，**不是 LLM 生成**。

### 4.3 美术链路挂在别处，本模块没消费

GDM 里其实有美术需求（`assets_needed`），`art_director.py` 也会产美术指导书——但场景生成这条链**从 IR 到 .tscn 完全没有消费美术信息**。美术链（`asset_forge` / `ai_image_client`）是挂在**预览端点**上的，不在 workflow 的场景生成里。

| 编号 | 问题 | 严重度 | 状态 |
|---|---|---|---|
| M4-01 | scene_generator 走图外并行，绕过 leader 分发；计划里的 scene 任务被"跳过但标记完成" | **高** | 未处理 |
| M4-02 | 并行导致 scene 可能引用未生成脚本，需 `_sanitize_scene_scripts` 删引用补丁 | **高** | 未处理（M4-01 的后果） |
| M4-03 | `EntityIR` 无任何视觉字段，产出必然是纯色块 | **高** | 未处理 |

| M4-06 | 美术信息未被场景生成链消费（美术链挂在预览端点） | 中 | 未处理 |

## 6. 改造建议（按投入产出比排序）

**第一步：接线归位（中成本，先做）**

1. M4-01：scene 任务移出 `_NON_CODE_TASK_TYPES`，改由 leader 按类型分派给 `scene_generator`；`scene_generator` 从 `asyncio.create_task` 并行改为图内节点（或串行阶段）
2. M4-02：串行后 `_sanitize_scene_scripts` 可废弃（保留为兜底），不再需要删引用

**第二步：补视觉字段（中高成本，动 schema）**

3. M4-03：`EntityIR` 增加 `color` / `size` / `sprite` / `animation` 等可选字段，默认值保证向后兼容；`.tscn` 生成侧消费这些字段
4. M4-06：把 `art_director` 的美术指导书（或 `assets_needed`）作为输入传入场景生成，让 IR 带上视觉意图

**第三步：扩大模板覆盖（低成本）**

5. M4-04/M4-05：把剩余 15 个品类补上模板，模板改为"蓝图参数化"而非固定坐标

> 注意：第二步动的是核心 schema，影响 `.tscn` 生成、预览端点、配方库（配方存了 scene_ir），**必须出方案审批后再实施**。
