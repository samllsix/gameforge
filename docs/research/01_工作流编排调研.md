# M1 · 工作流编排模块调研

> **调研范围**：仅 `src/core/graph/workflow.py` 单文件（1972 行）。结论、代码位置、行号均出自对该文件的走读与实跑验证；其他模块只作为"被调用方"出现，不展开其内部实现。
>
> **一句话结论**：原设计是"模拟软件团队分工"，实际代码里**技术 leader 退化成了发牌器、三分之一的计划任务被假装完成、两类专业人员无对象可分派**——理念塌掉了后半截，而不是设计方向错了。

---

## 1. 设计理念：模拟软件团队

README 与实际代码共同体现的原意：

```
用户自然语言输入
   ↓
需求分析师（requirement_analyzer）→ 把口语拆成结构化规格（Game Spec）
   ↓
设计师（game_designer）→ 写设计文档 GDM（品类/核心循环/实体/胜负条件）
   ↓
计划员（planner）→ 拆成任务计划，标注依赖先后
   ↓
技术 leader（orchestrator）→ 按任务类型派给对应角色
   ↓
干活的（code_generator 等）→ 交付代码
```

这个"软件团队"的比喻是对的，README 也是这么宣传的（宣称 10 个 Agent 分工协作）。**但实现只兑现了前半段。**

---

## 2. 三个关键纠正：理念与代码的落差

### 2.1 纠正一：leader 不"找人"，它只按顺序发牌

按理念，leader 应该看任务类型分派——美术的给美术、前端的给前端、测试的给测试。

实际代码（`src/core/graph/workflow.py:368`）只会做一件事：

```python
ready_tasks = self._get_all_ready_tasks(task_plan)
next_task = ready_tasks[0]                     # 只取第一个 → 串行，不是并行
return {"current_task_id": next_task["id"]}    # 交给同一个 code_generator
```

不管任务标题是「写玩家控制」还是「画个图标」，来的都是同一个 `code_generator`。方法名叫 `_get_all_ready_tasks`（"所有"），实际只派 `[0]`。

**真实情况：一个全能工人照着清单一项项做，不是一群专业人员分工。**

### 2.2 纠正二：非代码任务被"假装完成"

按理念，计划员清单上的「搭场景」「写 UI」「写文档」应交由对应角色执行。

实际代码（`src/core/graph/workflow.py:526`）：

```python
_NON_CODE_TASK_TYPES = {scene, documentation, config, ui, ...}
# 命中 → 标记 completed，跳过，什么都不做
```

实测运行日志：

```
task_skipped_non_code  task_id=task_004  type=documentation
task_skipped_non_code  task_id=task_005  type=documentation
```

「跳过」却标记成「完成」——这样依赖它的后续任务就能解锁，流程能继续。算个聪明的绕过，**但意味着计划清单上约 1/3 的任务是空转的**。

场景不是没做，而是绕过了整套分发：场景生成另起一条并行线，不归 leader 管（见 3.2）。

### 2.3 纠正三：UI、音频两类"专业人员"无对象可分派

`src/agents/` 下的接线实况：

| Agent | 接线状态 |
|---|---|
| requirement_analyzer | ✅ 接进图，归 leader 调度 |
| game_designer | ✅ 接进图 |
| planner | ✅ 接进图 |
| code_generator | ✅ 接进图 |
| scene_generator | ⚠️ 已接线，但走**图外并行**，不归 leader 调度 |
| **ui_generator** | ❌ **零接线**（759 行实现 + 700 行测试全部空转） |
| **audio_generator** | ❌ **零接线** |

验证方式：`grep -rn "ui_generator\|audio_generator" src/core/graph/workflow.py` → **零命中**。

**结论：买了两个专业人员，工位装修好了（含完整测试），但从没叫他们上过班。** 对 leader 而言，就是"想分派也没有对象可分"。

## 3. 技术细节补充（走读发现）

### 3.1 图的真实形状：5 个节点，4 个是转发器

```
requirement_analyzer ─→ game_designer ─→ planner ─→ orchestrator ─→ code_generator
                                                     ↑                    │
                                                     └──── continue ──────┘
                                                 （无 ready 任务 → END）
```

4 条固定边 + 1 条条件边（`_route_after_code_generator` :389 判 `is_complete`）。除 orchestrator 外，每个节点都是 `try: await self.xxx.execute(state) except: 记 error_log` 一行转发。

原 design 里的 `code_reviewer` / `refactor` / `test_generator` / `debugger` / `main_reviewer` **没有独立文件**，被折叠为 `CodeGeneratorAgent.run_pipeline()` 内的普通方法调用——所以这些"协作"在图和时序图上完全不可见。

### 3.2 真正掌握流程的是图外那两个入口方法

LangGraph 图只覆盖"策划 + 派活"一段（约全流程 1/6）。真实阶段顺序硬编码在 `run_with_streaming()` 方法体里：

```
├─ Sandbox.create()            # sandbox.enabled 时建任务工作区
├─ _run_recipe()               # ① 抄近路，命中则跳过 LLM 直接 return
├─ _run_scene_generation()     # ② asyncio.create_task 图外并行（场景线）
├─ graph.astream_events()      # ③ 【唯一在图内的一段】
├─ _post_process()             # ④
├─ _try_godot_pipeline()       # ⑤ 落盘 + 编译 + 建场景
├─ _run_verification_chain()   # ⑥ 闸门 → 冒烟 → 沉淀配方 → playtest
└─ event_callback("complete")  # ⑦ SSE 推送
```

LangGraph 实际只买到三样东西：**状态自动合并**（`code_generated` 用 `merge_dicts` 合并不互覆盖，`error_log`/`warnings` 用 `add` 追加）、**SSE 事件源**（前端实时进度全靠它）、**递归保护**（`recursion_limit` 防任务依赖成环）。没买到：检查点持久化、并行执行、可视化调试。

### 3.3 任务状态靠"整体替换"传递，漏返回就死循环

`task_plan` **没有 reducer**（对比 `code_generated` 有 `merge_dicts`）。`_mark_task_completed()` 返回整份新计划，节点以 `{"task_plan": ...}` 整体替换。源码注释记录了实测踩坑：占位产物走异常分支时返回的 dict 不含 `task_plan`，完成状态落不了地 → **无限重派**。

### 3.4 图外写、图内读，字段必须手工合并

场景生成跑在图外，写的是 `ainvoke` 之前的原始 dict；图返回的是通道快照。所以两个入口末尾都要把 6 个键手工捞回：

```python
for _key in ("scene_status", "scene_description", "scene_path",
             "scene_error", "scene_compile_errors", "scene_ir"):   # scene_ir 是调研期间补的
    if _key in state: final_state[_key] = state[_key]
```

`scene_description` 当年就丢过一次（源码有注释），本次发现 `scene_ir` 也漏了。

### 3.5 两条入口的验证强度曾经不一致（调研期间已修）

`run()`（批处理）此前在 `_try_godot_pipeline` 后就 return，gd-guard / 冒烟 / playtest 全不跑——**批处理与同步接口等于没有验证**。已抽为 `_run_verification_chain()`（:1614）两入口共用，批处理实测 `runnable=True`。

### 3.6 三处死代码

| 符号 | 位置 | 现状 |
|---|---|---|
| `_route_next` | :395 | 死的，仅在 SSE 事件过滤名单里作为字符串出现 |
| `_wrap_code_node` | :232 | 死的，仅测试调用（本想给节点包沙箱同步，后改用别的方式实现） |
| `_godot_compile_loop` | :650 | **无生产调用方**，仅测试用；且其 8765 HTTP 回退分支有 `NameError`（`client` 未定义 :685）——坏了没人发现 |

这三处说明"图曾经设计得比现在大"（有条件路由、有节点包装器、有独立编译闭环），后来退化成硬编码流程，但代码没清。

## 5. 改造建议（按投入产出比排序）

1. **把 leader 改成真调度员**（中成本、高收益）：按任务类型分派给对应 Agent；`ui_generator` / `audio_generator` 接线（代码和测试现成）；`_NON_CODE_TASK_TYPES` 里的 `ui` / `documentation` 不再假装完成。`_get_all_ready_tasks` 本就返回列表，支持并行派发，**这是把塌掉的后半截接回去，不是重新设计**。
2. **把图做诚实**（低成本）：清理 M1-09 三处死代码；图外阶段顺序抽成一张显式阶段表，两个入口退化为执行器。
3. 不建议第一步就把后段塞进图里——reducer 合并语义要重新设计，风险高。
