# 00 · 总体串联方案（01–06 的归口总纲）

> **本文定位**：`01_工作流编排` ~ `06_Godot引擎集成` 六篇是分模块调研，本文把它们归到一个框架下。**没有本文，那六篇只是 43 个散点；有了本文，它们是一套约定的 8 个条目。**
>
> **一句话结论**：6 个模块 43 个编号问题的**病根是同一个**——同一个问题全项目有多个模块各自回答且答案不一致。串联不是"再修 43 个 bug"，而是**定义 8 个收口点，让每个问题在全项目只有一个答案**。

---

## 1. 病根诊断：同一个问题，多个答案

| 问题 | 现在有几个答案 | 谁在答 |
|---|---|---|
| **项目目录在哪** | **4 种** | `paths.project_dir` / `api._resolve_preview_project` / `godot.project_path` / `os.getcwd()` |
| **谁派活** | **2 份**（一份没人用） | `workflow._orchestrator_node` + `OrchestratorAgent` |
| **LLM 怎么调** | **2 套**（保护不对等） | `chat()` 有熔断/缓存/指标，`chat_sync()` 全无 |
| **场景怎么生成** | **2 条**（互不知情） | 图外并行 create_task + `_NON_CODE_TASK_TYPES` 跳过 |
| **安全闸门接哪** | **5 个执行面只接 2 个** | workflow 冒烟前 + 导出门禁；漏预览渲染、沙箱 merge |
| **失败了怎么办** | **3 种风格** | 静默降级 / 抛错记日志 / 失败开放裸放过 |

已有一个做对了的样板：**`src/core/paths.py`**——零依赖、全项目只有它构造路径、docstring 内写验收约束（`grep '"projects"'` 除它之外必须为空）。本方案就是把它的模式推广到其余 7 个问题上。

---

## 2. 八个收口点

| # | 收口点 | 形态 | 新建/复用 |
|---|---|---|---|
| 1 | **路径** | `src/core/paths.py` | 已有，补测试锁定 |
| 2 | **引擎对接** | `GodotSession`（executable / project_dir / env） | 新建 `src/engine/godot/session.py` |
| 3 | **派活** | `OrchestratorAgent.get_next_task()` | 已有，删 workflow 重复实现 |
| 4 | **内容生成** | Agent 层编制补齐（ui/audio 归队、5 角色独立） | 扩建 `src/agents/` |
| 5 | **LLM 调用** | 单一入口（chat/chat_sync 合一 + 错误分类 + 空回复检测） | 改 `src/utils/llm_client.py` |
| 6 | **安全** | 一个 gate 模块，接满所有执行面 | 已有 `gd_guard.py` + `_gd_guard_scan`，重新组织 |
| 7 | **阶段顺序** | 阶段表（数据驱动），`run()` 与 `run_with_streaming()` 共用 | 改造 `workflow.py` |
| 8 | **失败策略** | 明确三分：降级 / 抛错 / 熔断，**禁止静默** | 跨模块约定 + 测试锁定 |

## 4. 实施分期（按风险从低到高）

### 期一 · 纯接线，零 schema 风险（建议先做）

| 内容 | 编号 | 验收 |
|---|---|---|
| 修 scene_generator 的 cwd 回落 | M6-01 | 空 `GODOT_PROJECT_PATH` 下 `.tscn` 落 `projects/<pid>/`，`git status` 干净 |
| 删 WebSocket 整套 + 8765 通路 + 插件 UI | M6-02/03/04、M1-07 | -1310 行；工作流/预览/导出三链实测仍通 |
| 抽 `GodotSession`，收 6 处 editor_path | M6-06/07 | 不设 `GODOT_EDITOR_PATH` 也能自动发现引擎 |
| 预览端点 + sandbox merge 接闸门 | M5-03、M6-08、M5-09 | 含 `OS.execute` 的项目 `GET /preview/frame` 返回 403 |
| 闸门失效显式化（`/health` 暴露） | M5-02 | 删二进制后 `/health` 立刻显示不可用 |
| 删 workflow 的派活重复实现，改调 OrchestratorAgent | M1-03、M2-01 | `grep "self.orchestrator.execute\|get_next_task"` 有真实调用 |

### 期二 · 动调用链，需回归保驾

| 内容 | 编号 | 验收 |
|---|---|---|
| ui_generator / audio_generator 接线，非代码任务不再假装完成 | M2-02、M4-02 | 任务清单里 ui/audio 任务有真实产物而非 skipped |
| 5 个审核角色独立成 Agent | M2-03、M2-04、M2-07、M1-02 | `fix_code` 的 5 处直达改为统一反馈接口；code_generator 行数下降 |
| scene_generator 归队走图内分发 | M4-01、M2-06 | `_sanitize_scene_scripts` 可退化为兜底；scene 任务状态机可见 |
| LLM 统一入口 + 错误分类 + 空回复检测 | M3-01~04 | 401 不再重试 16 次；空回复抛错而非静默降级 |
| 阶段表化，两入口合一 | M1-01、M1-04 | `run()` 与 `run_with_streaming()` 共用同一张阶段表 |

### 期三 · 动 schema，独立立项

| 内容 | 编号 | 前置条件 |
|---|---|---|
| `EntityIR` 增加视觉字段（color/size/sprite/animation） | M4-03 | 需先出 schema 变更方案，评估对 `.tscn` 生成 / `.scene_ir.json` / 配方库的影响 |
| 美术指导书接入场景生成链 | M4-06 | 依赖 M4-03 |
| 剩余 15 个品类的模板化 | M4-04、M4-05 | 依赖 M4-03 |

## 5. 风险与止损

| 风险 | 说明 | 止损 |
|---|---|---|
| **半收口状态** | 8 个收口点不可能一次做完，中间停下时系统是"半散半收" | 每期独立可回滚；期一内每项独立提交 |
| **期二动核心链** | Agent 补齐会影响配方库、预览端点、评测三处依赖 | 先补测试再动手；每项一提交 |
| **期三动 schema** | `EntityIR` 加字段会波及三处消费者 | 默认值保证向后兼容；旧配方不爆 |
| **测试基线漂移** | 现在 583 passed 是唯一安全网 | 每期结束必须全量回归，不允许下降 |

## 6. 明确不做的

- **不上 AST / 语义分析引擎**（gd-guard 的子串匹配上限就认下来，改为文档如实描述能力边界）
- **不做网络隔离**（依赖 gd-guard 拦 API 层）
- **不重做 LangGraph 图**（维持"图只覆盖策划+派活"的诚实定位）
- **不动 `src/adapters/`**（另一套空转 LLM 实现，标记为技术债但不投入）

---

## 7. 一句话给决策者

> **期一做完，这个项目的"工程质量"才配得上它的代码量；期二做完，"多智能体协作"才从宣传变成事实；期三做完，产出才配叫"游戏"而不是"三个方块"。三期独立验收、独立回滚，任意一期停下都不破坏前面成果。**
