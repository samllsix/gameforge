# GameForge 生成质量诊断

> **诊断对象**：为什么生成出来的游戏"感觉质量差"，以及能否达到前沿模型的直接生成水平。
> **方法**：抽查 6 个真实生成项目的产物构成 + 读取运行时脚本自述 + 核对评测报告实际分数。
> 生成时间：2026-09-16

---

## 0. 结论先行

**质量问题不是 bug，是设计取舍的必然结果。**

项目当前架构把"AI 生成游戏"这个命题，**渐进地转化成了"AI 配置游戏模板"**。为了让产物"必定能跑"，LLM 的职责被收窄到只剩"选模式 + 填参数 + 摆位置"，真正决定游戏好不好玩的那部分——玩法逻辑——是**人工预置、零生成**的。

这带来一个反直觉的结果：**产物能跑，是因为它本来就能跑**（预置件已经跑过无数遍），而不是因为 AI 做对了什么。

**并且当前系统没有能力感知"质量差"**——评测指标全是流程指标，最新一份报告 `overall_score = 100.0`。

### 1.3 决定性证据：运行时脚本的自述

`projects/grid_snake_demo/addons/gameforge/runtime/grid_runtime.gd:1-4`：

```gdscript
extends Node2D
## GameForge 网格游戏确定性运行时 —— 贪吃蛇 / Pong / 2048 / 打砖块 / 推箱子 / 扫雷
## 一个脚本覆盖六个品类：LLM 只决定 mode 参数，玩法零生成、零修改。
## 胜负通过 game_flow（组 "game_flow"）上报；分数增量上报。
```

**"玩法零生成、零修改"** —— 这是作者自己写下的设计意图，也是质量上限的直接来源：

> 玩法复杂度的天花板 = `grid_runtime.gd` 这 19.9 KB 能实现的东西。

同理，`src/engine/godot/scene_to_godot.py:759` 起的 `RUNTIME_SCRIPTS` 字典里，`mover.gd`（20 行）、`bouncer.gd`（13 行）、`rotator.gd`（8 行）都是这种极简通用件，且视觉基于 `extends ColorRect`（程序化色块，无贴图精灵）。

三项指标分别是：**语法能否编译**、**计划任务是否标记完成**、**Godot 兼容性**。

**没有一项与"游戏好不好玩"有关**，而且它们本质上是"流程是否走完"的自证指标——
`task_completion` 尤其如此：任务是系统自己拆的，完成标准也是系统的，自己给自己打分必然 100。

> **这是一个度量盲区**：系统既生成不出好游戏，也没有能力发现自己生成得不好。

### 1.6 更深一层：验证与度量层存在**静默失效**

Unity → Godot 的迁移只做完了主干，**所有验证与度量相关的模块仍留在 Unity 语义上**。
它们不会报错、不会告警，只会静默跳过每一个 `.gd` 文件。

实测清单：

| 位置 | 现状 | 后果 |
|------|------|------|

| `utils/code_validator.py` | **整个模块是 Unity C# 校验器**（`validate_unity_code`、`_check_unity_lifecycle_spelling`，全文判 `.cs`） | 对 Godot 项目**零检查** |

> 两层叠加的结果是：一个既生成不出好游戏、又测不出自己不好的系统。

### 1.7 归因修正：视觉并非"没有资产"（本文档早期判断有误）

**修正一处错误判断**：本文档初版据 `RUNTIME_SCRIPTS` 里 `extends ColorRect` 推断"视觉是程序化色块、无贴图精灵"。
复核实际产物后，**该判断不成立**：

| 项目 | AI 生成贴图 | 是否被场景引用 |
|------|------------|--------------|
| `GameForge_Project` | **11 张**（background / decoration / enemy×3 / ground / icon / npc / pickup / platform / player，均 200 KB 级） | ✅ 全部引用 |
| `e2e_playable5` | **11 张**（同上） | ✅ 全部引用 |
| `demo_jump_v2` | 6 张（background / enemy / pickup / player / icon / concept） | ✅ 全部引用 |
| `grid_snake_demo` | — | 网格游戏，程序化绘制（**设计如此，非降级**） |
| `space_demo` | 无 assets 目录 | 疑似失败产物 |

资产管线（`asset_forge.forge_assets` ← `scene_to_godot.write_project:1832`）**完整工作**，
`.env` 中 `STEP_API_KEY` / `SENSENOVA_API_KEY` 均已配置。`grid_snake_demo` 的色块是**该品类的正常表现**，
不是资产生成失败的证据——**初版把它当成了普遍现象，这是抽样错误**。

**"画面简陋"的真实归因**因此需要改写：

1. 贴图是生图模型的**一次性产物**，缺少风格一致性约束（同一场景里 player / enemy / ground 可能风格不统一）
2. 无图集（atlas）、无美术规范、无尺寸与朝向对齐
3. 角色动画是程序化拼的序列帧——`character_anim.py:7` 自述"（不完美，但保证 AnimatedSprite2D 有可播动画）"

> **这个纠错本身是本节最有力的论据**：
> 我抽样 6 个项目就得出了一处错误结论，**因为项目没有可靠的度量供我验证**。
> 当"问题是什么"都只能靠抽样推断时，推断必然出错——这是 P0 必须先行的经验证据，不是我的猜测。

### 1.8 四项投诉的根因分类（决定哪些能治、哪些治不了）

| 你的感受 | 根因 | 我的路径能否解决 |
|---------|------|----------------|
| 玩法太浅、内容少 | 玩法零生成，玩法上限 = 预置件能力（19.9 KB `grid_runtime`） | ✅ **能**（P1 放开生成边界） |
| 手感差、反馈弱 | 运行时是通用件（`player.gd` 57 行等），无加速度/缓动/coyote time/跳跃缓冲等手感调优 | ❌ **不能**——需专门的手感打磨，与"生成更多内容"无关 |
| 画面简陋、像原型 | 资产管线工作，但产物是一次性生图，无一致性/图集/动画精修 | ❌ **不能**——是资产**质量**问题，不是资产**有无**问题 |
| 每次都像同一个游戏 | 品类匹配命中 20 基款即套模板 + 模板优先 + 配方库复用 | ⚠️ **部分**——需多样性机制（比 P1 更根本） |

**四项是四种不同根因，不存在"一键方案"。** 而且其中三项的瓶颈**都不在"模型的生成能力"上**——
这意味着"更接近 AGIC 水平"**不能解决它们**：更强的模型能生成更多样、更正确的内容，
但解决不了**手感打磨**和**美术品质**，那两项是设计工作与资产工作。

## 2. 为什么会变成这样：一条自洽但方向单一的取舍链

项目最高优先级写在 `docs/gameforge-optimization-plan.md:3-4`——**"稳定生成真实可运行的游戏"**。
为达成它，做了三个各自都合理、合起来锁死上限的决策：

| 决策 | 解决的问题 | 副产物（代价） |
|------|-----------|--------------|
| **玩法零生成**（预置确定性运行时） | LLM 写玩法必然写错，报错改不完 | 玩法深度锁死在预置件内 |
| **gd-guard 禁 API**（网络/文件/进程） | 生成的脚本可能干危险的事 | 无法做联网、存档、动态内容 |
| **模板优先于 LLM** | 稳定、快、免费、可控 | 输出高度趋同，同类需求产出同一款游戏 |

三者叠加的效果：

```
追求「必定能跑」→ 收窄生成边界 → 产物 = 预置件 + 参数配置
                              ↓
                    能跑 ✅   但玩法深度 ❌  视觉表现 ❌  多样性 ❌
```

**这不是失误，是把"避免失败"做到了极致。** 观察四道验收闸门的形态就很清楚：
gd-guard 是**一票否决**、编译校验是**一票否决**、冒烟是**通过/不通过**、playtest 也是 `ok: true/false`。

**当验证只能回答"对/错"时，生成端最理性的策略就是"什么都不做"**——因为任何创新都可能触发否决。

## 3. 关于"达到前沿模型直接生成水平"

> 说明：我理解你问的是"能不能让 AI 直接生成出接近通用大模型手写质量的可玩游戏"。
> 如果你的 "agic" 指的是某个具体产品或指标，请纠正我。

### 3.1 换更强的模型，几乎不会改善

这是最需要先接受的一点。当前架构下 LLM 的职责是"**选 mode + 填参数 + 摆位置**"：

```
需求 "做一个贪吃蛇"
    ↓
LLM 做三件事：① 选 mode="snake"  ② 填速度/网格/配色  ③ 排布节点位置
    ↓
产物 = main.tscn（9.7 KB，摆在哪）+ runtime/（28 KB，预置，玩法零生成）
```

把模型从 deepseek-v4-flash 换成任何更强的模型，**产物仍然是同一个贪吃蛇**——
因为没有任何环节需要更强的模型能力。换了模型却看不到质量提升，会让人误判"模型不行"，
实际是**架构没有给模型留发挥空间**。

### 3.2 真正的瓶颈是三个，与模型无关

| # | 瓶颈 | 证据 |
|---|------|------|
| 1 | 生成边界太窄 | "玩法零生成、零修改"（`grid_runtime.gd:3`） |
| 2 | 没有质量度量 | `overall_score=100`，且 `.gd` 不参与质量指标计算 |
| 3 | 验证只能一票否决 | 四道闸门全是 bool，反馈粒度不足以支撑"放开" |

### 3.3 能到什么程度（诚实分层）

| 目标 | 判断 | 理由 |
|------|------|------|
| 单机小游戏"内容量和变化"上去（多关卡、道具、数值曲线、Boss、多敌人类型） | ✅ **现实** | 靠放开生成边界 + 保留骨架，不需要新模型 |
| 单品类游戏达到"普通人手写 Demo"的可玩完整度 | ✅ **可达**，但需重做验证粒度 | 关键是让验证从"对/错"变成"哪里不对" |
| 商业级手感 / 美术表现 / 内容体量 | ❌ **靠生成代码解决不了** | 这是资产管线问题，而资产管线被明确砍掉（"不碰 3D 素材管线"） |
| "一句话生成一个能卖的游戏" | ❌ **短期不现实** | 瓶颈不在模型，在验证闭环 + 资产生产 |

**一句话**：从"能跑"到"好玩"，要换的不是模型，是**风险承担方式**。

## 4. 提升路径（按投入产出比排序）

> **必须先纠正一个常见误读**：本节**不是"直接提升游戏质量"的路径**。
> P0 只给你测量能力，不改善任何产物；P1 改善的是内容量，不改善手感与画面。
> 这条路径真正保证的是——**让"改进质量"这件事从不可操作变为可操作**。
> 在此之前，你无法区分"改好了"和"改坏了"，因为你现有的报告恒为 100 分。

### P0 — 先让系统能"看见"质量（不做这个，后面全是盲调）

**P0-a 修复静默失效**（半天内可完成，风险为零）。按收益排序：

| # | 动作 | 位置 | 预期效果 |
|---|------|------|---------|
| 1 | `.cs` → `.gd` | `eval/metrics/__init__.py:302,311` | **质量/命名指标第一次生效** |
| 2 | `.cs` → `.gd` | `utils/consistency_validator.py:78` | class 名/文件名一致性检查对 Godot 生效 |
| 3 | 删掉 Unity 术语与"合法C#标识符"约束 | `agents/game_designer/__init__.py:461,478` | 停止污染 LLM 输出 |
| 4 | 默认引擎改为 `godot` | `api/main.py:483`、`eval/test_cases/__init__.py:23` | 消除默认值歧义 |
| 5 | `.cs` → `.gd` 统计 | `cli.py:226` | CLI 统计可用 |
| 6 | 删除或重写 | `utils/code_validator.py`（整文件） | 消除"看起来在检查、其实没检查"的模块 |

> ⚠️ **做完第 1 项后，评测分数会立刻下降。这是好事——指标终于开始说真话了。**
> 如果分数没变，说明指标仍未生效，要回头查。

**P0-b 新增玩法维度指标**。流程指标之外，需要能回答"这款游戏有多少玩法"：
   - 交互类型数（按键/鼠标/碰撞触发的种类）
   - 游戏状态数与状态转移数
   - 胜负条件复杂度
   - 可玩时长（playtest 能跑多久不结束）
   - 独立机制数（在预置件之外，有多少本项目专属逻辑）
3. **修 `_refactor` 空转**（`code_generator:1163-1170`）——它本该是质量提升环节。

### P1 — 分级放开生成边界（核心动作，但**需 P2 先行**）

> ⚠️ **依赖关系修正**：本节依赖 P2 先落地。**没有细粒度验证就放开边界，等于放弃控制**——
> 你会得到更多"能跑但不知道哪里不对"的产物。正确顺序是 **P0 → P2 → P1**。
>
> ⚠️ **另一个必须说清的边界**：放开边界增加的是**内容量与变化**，而 **"内容量" ≠ "好玩"**。
> 一个游戏可以有很多关卡却依然无聊。本节能改善的是"太浅、太快玩完、每次都一样"，
> 改善不了**手感、反馈、视觉表现**——那三项由预置件设计与资产管线决定，与生成边界无关。

不是"全放开"，而是**每次只放开一格，并配套加一道验证**：

| 级别 | 内容 | 风险 | 配套验证 |
|------|------|------|---------|
| L0（现在） | LLM 选 mode + 填参数 | 极低 | — |
| L1 | LLM 生成**实体表**：敌人类型/道具/数值曲线/关卡布局 | 低 | IR 与产物一致性校验 |
| L2 | LLM 生成**玩法规则**：胜负条件组合、机制开关、关卡序列 | 中 | 玩法断言（见 P2） |
| L3 | LLM 在预置基类上写**派生脚本**（`extends GFGridActor`） | 高 | gd-guard 白名单 + 冒烟 + playtest |

**关键认识**：L1 的收益远大于 L3，而风险远低于 L3。**当前最该做的不是让 LLM 写代码，而是让它写"结构"**——
它现在连"这个游戏有几关、每关有多少敌人、敌人怎么变强"都不能决定，这才是"玩法单薄"的直接原因。

### P2 — 把验证粒度从"对/错"改成"哪里不对"

这是**能换来质量的关键**，也是 P1 放开边界的前提。

- 现状：`gd-guard: block`、`compile: pass/fail`、`smoke: runnable/not`、`playtest: ok/not ok`。
  反馈粒度太粗 → 生成端只能保守。
- 目标：能输出**定位性反馈**，例如"第 3 关的敌人在玩家出生后没有移动"。
- 落地手段：**玩法一致性检查**——比对 IR 声明的玩法与 playtest 实际发生的玩法。
  例：IR 声明"玩家可以跳跃"，那么 playtest 轨迹里 `player.position.y` 必须出现过变化；
  声明"有 3 种敌人"，那么实际加载的敌人类型应 ≥3。

> **这个检查一旦建立，L1/L2 就可以安全放开了**——因为系统终于能区分"玩法没实现"和"实现得不好"。

### P3 — 真正用上模型能力

- 现状上限：编译修复 3 轮（`workflow.py:562`）+ playtest 修复 1 轮（`playtest.max_fix_attempts`）。
- 改进方向：让 playtest + VLM 的反馈进入**玩法改进**，而不只是"修 bug"。
  现在 VLM 的产出（`visual_review.py` 的五类失败模式：渲染失败/精灵错位/UI 不可读/风格混杂/相机越界）
  全是**缺陷检测**，没有一类是"这个玩法太单调"。
- 加一类失败模式：**玩法单薄**（如"全程只有一种交互"、"没有难度变化"），让它触发重设计而非修复。

---

## 5. 一句话总结

> 当前项目做的是 **"AI 配置游戏模板"**，它把"必定能跑"做到了极致，代价是玩法、视觉、多样性全部让位。
> **换更强模型不会改变产物**，因为架构没给模型留发挥空间。
> 要提升质量，先建立**能感知质量**的度量（P0），再让 LLM 从"填参数"升级到"填结构"（P1），
> 而这两步的前提是**把验证粒度做细**（P2）——让系统敢于放开，因为它能定位问题。

**Actionable 的第一步**：修 `eval/metrics` 的 `.gd` bug + 加"独立机制数"指标。
这两件事做完，你才第一次拥有"质量是否在提升"的客观依据。
